# 19. 韌體資訊安全

> **一句話**：連網裝置一旦被攻破，可能成為殭屍網路、洩漏隱私、甚至危害人身安全。**2027 年起歐盟 CRA 全面適用**，資安已從「加分」變成「產品上市的法定門檻」。

---

## 1. 為什麼韌體資安特別難 🟢

| 挑戰 | 說明 |
|---|---|
| 實體接觸 | 攻擊者可以拿到裝置拆開、接上除錯器、量測電源 |
| 長壽命 | 裝置可能在現場運作 10～20 年 |
| 資源受限 | 加密運算與安全機制吃 Flash/RAM/電力 |
| 更新困難 | 沒有 OTA 就無法修補漏洞 |
| 規模 | 同一把金鑰外洩 = 全部裝置淪陷 |

**經典案例**：**Mirai 殭屍網路（2016）**利用 IoT 裝置的**預設帳號密碼**，癱瘓了大型 DNS 服務商 Dyn。

## 2. 威脅建模 🟡

| 方法 | 說明 |
|---|---|
| **STRIDE** | Spoofing（冒用）、Tampering（竄改）、Repudiation（否認）、Information Disclosure（洩漏）、DoS、Elevation of Privilege（提權） |
| 攻擊面分析 | 除錯埠、通訊介面、無線、OTA、雲端 API、供應鏈 |
| **TARA** | 車用 ISO/SAE 21434 的威脅分析與風險評估 |
| 資產識別 | 金鑰、韌體智財、使用者資料、控制功能 |

## 3. 信任鏈與安全開機（Secure Boot）🟡

```
不可變的信任根（Root of Trust）：Boot ROM + OTP/eFuse 中的公鑰雜湊
   │ 驗證簽章
   ▼
第一階段 Bootloader（如 MCUboot）
   │ 驗證簽章
   ▼
應用程式韌體
   │（Linux：驗證 Kernel、dm-verity 驗證 rootfs）
   ▼
執行
```

| 觀念 | 說明 |
|---|---|
| **Root of Trust** | 必須不可修改：ROM 程式碼 + OTP 中燒錄的公鑰雜湊 |
| **簽章驗證** | 製造商用**私鑰**簽章韌體，裝置用**公鑰**驗證（ECDSA P-256 / Ed25519 / RSA-3072） |
| **Measured Boot** | 每一階段記錄雜湊值，供遠端證明（Remote Attestation） |
| **防降級（Anti-Rollback）** | 安全版本號存於單調計數器（OTP），拒絕舊版本 |
| **加密映像** | 韌體加密存放（防止智財外洩與分析） |

> **簽章 ≠ 加密**：簽章證明「是誰做的、沒被改過」；加密保護「別人看不懂」。Secure Boot 的核心是簽章。

## 4. 密碼學基礎（韌體需知）🟡

| 用途 | 演算法 |
|---|---|
| 對稱加密 | **AES-128/256**（GCM 或 CCM 模式提供加密 + 完整性） |
| 雜湊 | **SHA-256**、SHA-3 |
| 訊息驗證碼 | **HMAC-SHA256**、AES-CMAC |
| 數位簽章 | **ECDSA（P-256）**、**Ed25519**、RSA |
| 金鑰交換 | **ECDH（X25519、P-256）** |
| 金鑰衍生 | HKDF |
| 傳輸安全 | **TLS 1.3**、DTLS 1.2/1.3 |
| **後量子密碼（PQC）** | NIST 2024 年發布標準 **ML-KEM（FIPS 203）、ML-DSA（FIPS 204）**、SLH-DSA（FIPS 205）；韌體簽章也可用 **LMS / XMSS**（基於雜湊，CNSA 2.0 建議用於韌體簽章） |

**函式庫**：**Mbed TLS**、**wolfSSL**、PSA Crypto API、TinyCrypt（已逐漸淘汰）、libsodium、BearSSL。

**韌體常見錯誤**：
- **寫死金鑰在程式碼中**（反組譯即可取得）
- 使用 `rand()` 產生金鑰 → 必須使用 **TRNG**
- AES-ECB 模式（相同明文產生相同密文）
- 重複使用 nonce / IV（GCM 下會完全破功）
- 用 `memcmp` 比較 MAC → **時序攻擊**，應使用常數時間比較

## 5. 硬體安全功能 🔴

| 功能 | 說明 |
|---|---|
| **讀取保護（RDP）/ 除錯鎖** | 量產時關閉 JTAG/SWD 或禁止讀取 Flash（STM32 RDP Level 2 永久鎖定） |
| **TrustZone（ARMv8-M）** | 將 MCU 分成**安全世界**與**非安全世界**，金鑰與加密操作在安全世界 |
| **TF-M（Trusted Firmware-M）** | ARMv8-M 上的開源安全韌體，實作 PSA 安全服務 |
| **Secure Element / TPM** | 獨立安全晶片存放私鑰，**私鑰永不離開晶片**（NXP SE050、Microchip ATECC608、Infineon OPTIGA） |
| **PUF** | 物理不可複製函數：從晶片製程差異衍生唯一金鑰 |
| 硬體加密加速器 | AES、SHA、PKA、TRNG |
| 防篡改 | 開殼偵測、電壓/時脈/溫度異常偵測 |
| **OTP / eFuse** | 一次性燒錄：公鑰雜湊、安全設定 |

**PSA Certified**：ARM 主導的 IoT 安全認證框架（Level 1～4），對應 SESIP 等標準。

## 6. 實體攻擊 🔴

| 攻擊 | 說明 | 防禦 |
|---|---|---|
| **除錯埠存取** | 接上 SWD 讀出韌體 | 量產鎖定除錯埠 |
| **UART Console** | 未關閉的 shell | 量產關閉或需驗證 |
| Flash 讀取 | 拆下外部 Flash 讀取 | Flash 加密 |
| **故障注入（Fault Injection / Glitching）** | 電壓或時脈瞬間異常，讓 CPU 跳過指令（例如跳過簽章檢查） | 硬體偵測器、**重複檢查、隨機延遲**、使用非簡單布林值（如 `0x5AA5` 代表成功） |
| **旁通道攻擊（Side-Channel）** | 量測功耗/電磁/時間推算金鑰（DPA、SPA、時序攻擊） | 常數時間實作、硬體防護的加密引擎 |
| 冷啟動攻擊 | 讀取殘留 RAM | 用完即清除敏感資料 |

故障注入防禦範例（概念）：

```c
// 不好：單一布林判斷，一次 glitch 就能跳過
if (verify_signature(img)) boot(img);

// 較好：使用特殊值、重複檢查、反向檢查
volatile uint32_t r1 = verify_signature(img);   // 成功回傳 0x3CA5965A
volatile uint32_t r2 = verify_signature(img);
if (r1 == 0x3CA5965Au && r2 == 0x3CA5965Au && (r1 ^ r2) == 0) boot(img);
```

## 7. 軟體漏洞 🟡

| 漏洞 | 韌體情境 |
|---|---|
| **緩衝區溢位** | 解析封包時沒檢查長度（**最常見**） |
| 整數溢位 | `len + header` 溢位後通過檢查 |
| 格式字串 | `printf(user_input)` |
| 未驗證輸入 | 信任來自 BLE/UART/網路的長度欄位 |
| 不安全預設 | 預設密碼、開放的除錯命令 |
| 第三方元件漏洞 | 舊版 TCP/IP 堆疊（如 **Ripple20、AMNESIA:33** 影響數億裝置） |

防禦：**所有外部輸入都不可信**、長度檢查、MPU 隔離、堆疊保護（canary）、**XN（不可執行 RAM）**、模糊測試（**Fuzzing**：libFuzzer、AFL++ 在主機端測試解析器）、考慮記憶體安全語言（Rust）。

## 8. 安全 OTA 🟡

1. 傳輸加密（TLS）
2. **韌體簽章**（端到端：即使伺服器被入侵，沒有簽章私鑰也無法發布惡意韌體）
3. 裝置端驗證後才安裝
4. 防降級
5. 失敗回滾（A/B）
6. 簽章私鑰存放在 **HSM**，簽章流程受控與稽核

## 10. PSIRT 與漏洞管理 🟡

- 建立漏洞揭露管道（security.txt、Bug Bounty）
- 追蹤第三方元件 CVE（依 SBOM 比對）
- 評估（CVSS）、修補、發布安全公告
- 依法規時限通報（CRA：已被利用的漏洞需在 **24 小時內**提出早期預警）

## 面試常問

### Q1. 什麼是 Secure Boot？如何實作？

見第 3 節：從不可變的信任根開始，每一階段在執行下一階段前驗證其數位簽章，形成信任鏈。實作：Boot ROM 或不可更新的第一階段 Bootloader 內含（或從 OTP 讀取）公鑰雜湊，驗證 Bootloader；Bootloader（如 MCUboot）驗證應用程式；搭配防降級計數器與除錯埠鎖定。

### Q2. 簽章與加密的差別？Secure Boot 用哪個？

簽章用私鑰產生、公鑰驗證，提供**真實性與完整性**；加密提供**機密性**。Secure Boot 核心是簽章；若需保護韌體智財則再加上加密。

### Q3. 金鑰該如何存放在裝置中？

最佳：Secure Element / TPM / TrustZone 安全世界，私鑰在安全硬體中產生且永不匯出。次佳：OTP/eFuse 或受保護的 Flash 區域 + 讀取保護 + 除錯鎖定。絕不：寫死在程式碼、所有裝置共用同一把金鑰。

### Q4. 什麼是旁通道攻擊？如何防禦？

透過量測功耗、電磁輻射或執行時間等物理資訊推算出祕密資料（例如金鑰）。防禦：常數時間演算法（比較、查表不依賴祕密值）、使用具旁通道防護的硬體加密引擎、遮罩（Masking）、加入雜訊與隨機化。

### Q5. 什麼是故障注入攻擊？韌體如何緩解？

透過電壓、時脈、電磁或雷射干擾，使 CPU 跳過或錯誤執行指令，例如跳過簽章檢查或讀取保護。韌體緩解：重複檢查、使用 Hamming 距離大的特殊值而非 0/1、控制流程完整性檢查、隨機延遲；硬體緩解：電壓/時脈異常偵測器。

### Q6. 解析網路封包時，如何避免緩衝區溢位？

不信任任何長度欄位：檢查長度 ≤ 緩衝區大小、檢查 `offset + len` 不溢位且不超過實際接收長度；使用有長度參數的函式；以模糊測試驗證解析器；啟用 MPU 與堆疊保護作為縱深防禦。

### Q7. 歐盟 CRA 對韌體開發有什麼影響？

產品需在設計階段即納入資安（Secure by Design / by Default）、提供至少 5 年（或產品預期壽命）的安全更新、維護 SBOM、建立漏洞處理與通報流程，並在期限內通報被積極利用的漏洞。違規最高可罰全球營收 2.5% 或 1500 萬歐元。這讓**安全 OTA、SBOM、Secure Boot 成為必備能力**。

### Q8. 為什麼不能用 `memcmp` 比較 MAC？

`memcmp` 遇到第一個不同的 byte 就返回，執行時間洩漏了「前幾個 byte 正確」，攻擊者可逐 byte 猜出正確值。應使用常數時間比較（逐 byte XOR 後 OR 累積，最後判斷是否為 0）。

## 過時技術（知道就好）

- **只靠「隱藏」的安全（Security through Obscurity）**：例如自訂加密演算法、只靠讀取保護，已被證明無效。
- **SHA-1、MD5、DES、RSA-1024**：已不安全。
- **TLS 1.0 / 1.1**：已棄用，應使用 TLS 1.2 以上（首選 1.3）。

## 本章回顧

- 信任鏈：不可變 Root of Trust → 逐級驗證簽章
- 簽章證明來源、加密保護機密；金鑰放安全硬體
- 量產鎖除錯埠；防禦故障注入與旁通道
- 所有外部輸入都不可信；Fuzzing + MPU 縱深防禦
- CRA、EN 18031、ISO 21434、IEC 62443：SBOM + 漏洞管理 + 安全 OTA 已是法定要求
