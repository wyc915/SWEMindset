# 14. CI/CD 與 DevOps

> **一句話**：讓「程式碼合併」到「上線」變成自動、可重複、可回滾的流程。部署越頻繁、每次改動越小，風險反而越低。

---

## 1. 基本名詞 🟢

| 名詞 | 意思 |
|---|---|
| **CI 持續整合** | 每次提交都自動建置與測試，及早發現錯誤 |
| **CD 持續交付** | 程式隨時處於可部署狀態，按一下就能上線 |
| **CD 持續部署** | 通過測試就自動部署到正式環境 |
| **DevOps** | 開發與維運不再分家，共同為上線結果負責，並大量自動化 |

## 2. 典型流水線（Pipeline）🟢

```
提交程式碼
  → 程式碼檢查（Lint、安全掃描）
  → 建置
  → 單元測試
  → 打包成 Docker 映像檔並推送到 Registry
  → 自動部署到測試環境
  → 整合 / E2E 測試
  → （人工核准）
  → 部署到正式環境
  → 健康檢查，異常自動回滾
```

**主流工具**：GitHub Actions、GitLab CI、Azure DevOps Pipelines、Jenkins。

**重要原則**：
- **建置一次，部署多處**：同一個映像檔從測試環境一路推到正式環境，只換設定
- **流水線失敗要立刻修**，不要放著
- 環境：開發 → 測試 → 預備（Staging）→ 正式

## 3. 部署策略（面試必考）🟡

| 策略 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **重建** | 全部停掉再啟動新版 | 最簡單 | 會停機 |
| **滾動更新** | 一台一台換成新版（K8s 預設） | 不停機、不需額外資源 | 新舊版本會同時存在 → 程式與資料庫必須向後相容 |
| **藍綠部署** | 準備一套完整新環境，一次切換流量 | 回滾最快（切回去即可） | 需要兩倍資源 |
| **金絲雀部署** | 先放 5% 流量到新版，觀察指標正常再逐步放大 | 風險最小 | 需要完善的監控 |
| **Feature Flag** | 程式先部署但功能關閉，再用開關啟用 | 「部署」與「發布」分離，可針對特定使用者開放 | 開關太多要定期清理 |

## 4. 基礎設施即程式碼（IaC）🟡

**問題**：手動在雲端主控台點選建立資源 → 無法重現、無法審查、環境不一致。

**解法**：用程式碼描述基礎設施，放進 Git 管理。
- **Terraform**（及開源分支 OpenTofu）：跨雲最主流
- **Bicep**（Azure）、**CloudFormation**（AWS）：雲廠商原生
- **Ansible**：設定伺服器內部的軟體與組態

## 5. GitOps 🔴

**Git 是唯一的事實來源**：K8s 要部署什麼版本，全部寫在 Git 裡。工具（**Argo CD**、Flux）持續比對 Git 與叢集實際狀態，不一致就自動同步。

好處：所有變更都有紀錄、可審查、可回滾（還原 commit 即可）。

## 6. 衡量 DevOps 成效：DORA 指標 🟡

| 指標 | 意思 |
|---|---|
| 部署頻率 | 多久部署一次 |
| 變更前置時間 | 從提交到上線要多久 |
| 變更失敗率 | 部署後出問題的比例 |
| 恢復時間 | 出事後多久恢復 |

> 頂尖團隊的特徵：部署得又快又頻繁，同時失敗率低、恢復快。速度與穩定並不衝突。

## 7. 資料庫變更的部署 🟡

最容易出事的部分。原則：
- Migration 腳本版本化，隨流水線執行
- **不做破壞性變更**：要改欄位名稱時，先新增新欄位 → 程式同時寫兩邊 → 搬資料 → 程式只用新欄位 → 最後刪除舊欄位
- 這樣滾動更新時新舊版本都能正常運作

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. CI 和 CD 的差別？

- **CI（持續整合）**：開發者頻繁合併程式碼，每次提交**自動建置與測試**，及早發現整合錯誤。
- **CD 有兩種意思**：
  - **持續交付（Continuous Delivery）**：程式隨時處於可部署狀態，部署到正式環境需**人工按下核准**
  - **持續部署（Continuous Deployment）**：通過所有自動化檢查後**自動部署**到正式環境

順序是 CI → 持續交付 → 持續部署，自動化程度越來越高，對測試與監控的要求也越來越高。

### Q2. 藍綠部署與金絲雀部署的差別？各適合什麼情況？

- **藍綠部署**：準備兩套完整環境，藍（舊版）服務中時把綠（新版）部署好並驗證，再**一次切換全部流量**。有問題立刻切回藍。
  - 適合：需要**秒級回滾**、新舊版本不宜長時間共存的系統
  - 代價：需要兩倍資源
- **金絲雀部署**：新版先接**少量流量**（如 5%），觀察錯誤率與延遲正常再逐步提高到 100%。
  - 適合：使用者量大、想在**影響範圍最小**的情況下驗證新版
  - 代價：需要完善的監控與流量控制，新舊版本會共存一段時間

### Q3. 滾動更新時要注意什麼？

滾動更新期間**新舊版本會同時運作**，因此要注意：
- **向後相容**：API 與資料庫結構必須同時支援新舊版本，不能做破壞性變更
- **健康檢查**：設定好 Readiness Probe，新 Pod 準備好才導入流量
- **優雅關閉**：舊 Pod 收到終止訊號時，要處理完進行中的請求再結束
- **批次大小**：控制一次替換幾個（maxSurge / maxUnavailable），確保容量足夠
- **監控與自動回滾**：觀察更新過程中的錯誤率，異常時停止並回滾

### Q4. 如何在不停機的情況下修改資料庫欄位？

以「欄位改名」為例，採用 **Expand → Migrate → Contract** 分多次部署：
1. **擴充**：新增新欄位（允許 NULL），舊欄位保留
2. **雙寫**：部署新版程式，同時寫入新舊兩個欄位
3. **搬資料**：分批把舊資料複製到新欄位（避免長時間鎖表）
4. **切換讀取**：程式改為讀新欄位
5. **收斂**：確認所有版本都不再使用舊欄位後，才刪除舊欄位

原則：每一次部署都保證新舊版本程式都能正常運作，任何一步都可以回滾。

### Q5. 什麼是 IaC？有什麼好處？

**IaC（基礎設施即程式碼）**：用程式碼（Terraform、Bicep 等）描述伺服器、網路、資料庫等基礎設施，而不是在雲端主控台手動點選。

好處：
- **可重現**：一鍵建立完全相同的測試、預備、正式環境
- **版本控制與審查**：基礎設施變更也走 PR，有紀錄、可回溯
- **減少人為錯誤與環境差異**
- **災難復原快**：環境毀損時可用程式碼快速重建
- **自動化**：可整合進 CI/CD 流程

### Q6. 部署後發現問題，如何快速回滾？

事前準備決定回滾速度：
- **映像檔版本化**：每次部署都是有明確版本號的映像，回滾就是部署上一個版本（K8s：`kubectl rollout undo`；GitOps：還原 Git 提交）
- **藍綠部署**：直接把流量切回舊環境，最快
- **Feature Flag**：問題出在新功能時，直接關閉開關，不需重新部署
- **資料庫變更向後相容**：確保程式回滾後仍能使用目前的資料庫結構——這是回滾最常卡住的地方

原則：**先回滾止血，再查原因**。

## 過時技術（知道就好）

- **手動 FTP 上傳、遠端桌面複製檔案部署**：無紀錄、易出錯。
- **Jenkins**：仍被大量使用，但新專案多選 GitHub Actions / GitLab CI 等與程式碼平台整合的方案。

## 本章回顧

- 小步、頻繁、自動化部署 = 低風險
- 部署策略：要省資源選滾動，要快速回滾選藍綠，要低風險選金絲雀
- 基礎設施與部署狀態都放進 Git
