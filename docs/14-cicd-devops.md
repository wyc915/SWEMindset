# 14. CI/CD 與 DevOps

> **一句話**：讓「程式碼合併」到「上線」變成自動、可重複、可回滾的流程。部署越頻繁、每次改動越小，風險反而越低。

---

## 1. 基本名詞 🟢

| 名詞 | 意思 |
|---|---|
| **CI 持續整合** | 每次提交都自動建置與測試，及早發現錯誤 |
| **CD 持續交付** | 程式隨時處於可部署狀態，按一下就能上線 |
| **CD 持續部署** | 通過測試就自動部署到正式環境 |
| **DevOps** | 開發與維運不再分家，共同為上線結果負責，並大量自動化 |

## 2. 典型流水線（Pipeline）🟢

```
提交程式碼
  → 程式碼檢查（Lint、安全掃描）
  → 建置
  → 單元測試
  → 打包成 Docker 映像檔並推送到 Registry
  → 自動部署到測試環境
  → 整合 / E2E 測試
  → （人工核准）
  → 部署到正式環境
  → 健康檢查，異常自動回滾
```

**主流工具**：GitHub Actions、GitLab CI、Azure DevOps Pipelines、Jenkins。

**重要原則**：
- **建置一次，部署多處**：同一個映像檔從測試環境一路推到正式環境，只換設定
- **流水線失敗要立刻修**，不要放著
- 環境：開發 → 測試 → 預備（Staging）→ 正式

## 3. 部署策略（面試必考）🟡

| 策略 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **重建** | 全部停掉再啟動新版 | 最簡單 | 會停機 |
| **滾動更新** | 一台一台換成新版（K8s 預設） | 不停機、不需額外資源 | 新舊版本會同時存在 → 程式與資料庫必須向後相容 |
| **藍綠部署** | 準備一套完整新環境，一次切換流量 | 回滾最快（切回去即可） | 需要兩倍資源 |
| **金絲雀部署** | 先放 5% 流量到新版，觀察指標正常再逐步放大 | 風險最小 | 需要完善的監控 |
| **Feature Flag** | 程式先部署但功能關閉，再用開關啟用 | 「部署」與「發布」分離，可針對特定使用者開放 | 開關太多要定期清理 |

## 4. 基礎設施即程式碼（IaC）🟡

**問題**：手動在雲端主控台點選建立資源 → 無法重現、無法審查、環境不一致。

**解法**：用程式碼描述基礎設施，放進 Git 管理。
- **Terraform**（及開源分支 OpenTofu）：跨雲最主流
- **Bicep**（Azure）、**CloudFormation**（AWS）：雲廠商原生
- **Ansible**：設定伺服器內部的軟體與組態

## 5. GitOps 🔴

**Git 是唯一的事實來源**：K8s 要部署什麼版本，全部寫在 Git 裡。工具（**Argo CD**、Flux）持續比對 Git 與叢集實際狀態，不一致就自動同步。

好處：所有變更都有紀錄、可審查、可回滾（還原 commit 即可）。

## 6. 衡量 DevOps 成效：DORA 指標 🟡

| 指標 | 意思 |
|---|---|
| 部署頻率 | 多久部署一次 |
| 變更前置時間 | 從提交到上線要多久 |
| 變更失敗率 | 部署後出問題的比例 |
| 恢復時間 | 出事後多久恢復 |

> 頂尖團隊的特徵：部署得又快又頻繁，同時失敗率低、恢復快。速度與穩定並不衝突。

## 7. 資料庫變更的部署 🟡

最容易出事的部分。原則：
- Migration 腳本版本化，隨流水線執行
- **不做破壞性變更**：要改欄位名稱時，先新增新欄位 → 程式同時寫兩邊 → 搬資料 → 程式只用新欄位 → 最後刪除舊欄位
- 這樣滾動更新時新舊版本都能正常運作

## 過時技術（知道就好）

- **手動 FTP 上傳、遠端桌面複製檔案部署**：無紀錄、易出錯。
- **Jenkins**：仍被大量使用，但新專案多選 GitHub Actions / GitLab CI 等與程式碼平台整合的方案。

## 本章回顧

- 小步、頻繁、自動化部署 = 低風險
- 部署策略：要省資源選滾動，要快速回滾選藍綠，要低風險選金絲雀
- 基礎設施與部署狀態都放進 Git
