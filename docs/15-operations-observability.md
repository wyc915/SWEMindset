# 15. 維運與可觀測性

> **一句話**：上線不是結束而是開始。**你無法修復你看不到的問題**——可觀測性讓你在使用者抱怨前就發現異常。

## 學習目標

- 區分 Logs、Metrics、Traces 並說出各自回答的問題
- 用 OpenTelemetry 追蹤跨服務請求
- 定義 SLI / SLO，並用錯誤預算平衡開發速度與穩定性
- 執行事故處理流程，並訂定 RPO / RTO 與備份策略

---

## 1. 可觀測性三支柱 🟢

| 支柱 | 回答的問題 | 例子 | 常用工具 |
|---|---|---|---|
| **Logs 日誌** | 發生了什麼事？ | 「訂單 123 付款失敗：餘額不足」 | Serilog、ELK、Loki |
| **Metrics 指標** | 整體狀況如何？趨勢呢？ | 每秒請求數、錯誤率、CPU 使用率 | Prometheus + Grafana |
| **Traces 追蹤** | 一個請求經過哪些服務、卡在哪？ | API → 訂單服務 → 資料庫，總共 2 秒，資料庫佔 1.8 秒 | Jaeger、Tempo |

**OpenTelemetry（OTel）**：業界統一的收集標準，程式只要接 OTel，就能把資料送到任何監控平台。新專案優先採用。

商業整合平台：Azure Application Insights、Datadog、New Relic。

## 2. 日誌的好習慣 🟢

- **結構化日誌**（JSON 格式），方便搜尋與分析，而不是一串純文字
- **等級分明**：Debug / Info / Warning / Error / Critical，正式環境通常只開 Info 以上
- **帶上關聯 ID（Correlation / Trace ID）**：同一個請求跨多個服務時，可以串起所有日誌
- **不記錄敏感資料**：密碼、Token、完整個資
- 容器環境：日誌輸出到 stdout，由平台統一收集

## 3. 該監控什麼 🟡

**四大黃金訊號**（Google SRE 提出）：
1. **延遲**：請求多快
2. **流量**：請求量多少
3. **錯誤**：失敗比例
4. **飽和度**：資源快用完了嗎（CPU、記憶體、連線池、磁碟）

## 4. SLI / SLO / SLA 🟡

| 名詞 | 意思 | 例子 |
|---|---|---|
| **SLI** 服務指標 | 實際量測的數值 | 成功請求比例 |
| **SLO** 服務目標 | 團隊內部設定的目標 | 每月 99.9% 請求成功 |
| **SLA** 服務合約 | 對客戶的承諾，違反要賠償 | 99.5%，未達成退費 |

**可用性換算**：
- 99.9% → 每月約 **43 分鐘**可停機
- 99.99% → 每月約 **4.3 分鐘**

**錯誤預算**：SLO 99.9% 代表允許 0.1% 失敗。預算還多 → 可以加快發新功能；預算用完 → 暫停新功能，專心改善穩定性。

## 5. 告警 🟡

- **針對症狀告警**（使用者受影響，例如錯誤率升高），而非原因（CPU 80%）
- 每則告警都必須是**需要人採取行動的**，否則會造成「告警疲勞」，最後沒人理
- 分級：緊急（半夜叫醒）vs 一般（上班時間處理）

## 6. 事故處理 🟡

**流程**：
1. **偵測**：監控告警或使用者回報
2. **評估嚴重度**：影響多少使用者？
3. **止血優先**：先恢復服務（回滾、切換、擴容），**不是先找根因**
4. **溝通**：讓相關人員知道進度
5. **事後檢討（Postmortem）**：找出根因與改善行動，採**不究責**原則 —— 重點是改善系統，不是追究個人

**Runbook**：把常見問題的處理步驟寫成文件，半夜值班也能照著做。

## 7. 備份與災難復原 🟡

| 名詞 | 意思 |
|---|---|
| **RPO** | 最多能接受遺失多久的資料（例如 1 小時 → 至少每小時備份） |
| **RTO** | 最多能接受停機多久才恢復 |

- **3-2-1 原則**：3 份副本、2 種儲存媒介、1 份放異地
- **定期演練還原**：沒有測試過能還原的備份，等於沒有備份
- 防勒索軟體：保留無法被修改或刪除的備份

## 8. 維運基本功 🟢

- **Linux 基本操作**：檢視程序、權限、磁碟空間、日誌
- **網路排查**：`ping`、`curl`、`nslookup` / `dig`、檢查連接埠
- **12-Factor App**：設定由環境變數注入、程式無狀態、日誌輸出到 stdout 等現代雲端應用原則
- 定期檢查：**憑證到期**（常見事故原因）、磁碟空間、套件更新

## 動手練習

1. **接上 OpenTelemetry**：為兩個互相呼叫的服務加入 OpenTelemetry，送到 Jaeger（Docker 啟動），觀察完整追蹤。
2. **建立儀表板**：用 Prometheus + Grafana 建立 RED 指標（請求率、錯誤率、延遲）儀表板，並設定一個基於錯誤率的告警。
3. **還原演練**：替測試資料庫做備份，刪除資料後實際還原並計時，得出你的 RTO。

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. Logs、Metrics、Traces 的差別？

- **Logs（日誌）**：離散的事件紀錄，回答「**發生了什麼事**」，資訊最詳細。例：「訂單 123 付款失敗：餘額不足」。
- **Metrics（指標）**：數值的時間序列，回答「**整體狀況與趨勢如何**」，儲存成本低、適合告警。例：每秒請求數、錯誤率、P99 延遲。
- **Traces（追蹤）**：一個請求在多個服務間的完整路徑與各段耗時，回答「**慢在哪、錯在哪一段**」。

實務流程：Metrics 告警發現異常 → Traces 定位是哪個服務哪一段 → Logs 看詳細錯誤原因。

### Q2. 微服務架構下，如何追蹤一個請求的完整路徑？

使用**分散式追蹤**：
1. 請求進入系統時產生唯一的 **Trace ID**
2. 每個服務呼叫下一個服務時，透過 HTTP 標頭（W3C `traceparent`）或訊息屬性**傳遞 Trace ID**
3. 每段處理記錄為一個 **Span**（含開始時間、耗時、服務名稱）
4. 收集到追蹤系統（Jaeger、Tempo、Application Insights），組成完整的呼叫鏈與時間軸

實作上使用 **OpenTelemetry**，大部分 HTTP、資料庫、MQ 函式庫可自動產生 Span。日誌中也帶上 Trace ID，就能從追蹤直接找到相關日誌。

### Q3. SLA、SLO、SLI 的差別？

- **SLI（服務水準指標）**：**實際量測**的數值，例如「過去 30 天成功請求比例 99.95%」
- **SLO（服務水準目標）**：團隊**內部設定的目標**，例如「每月成功率 ≥ 99.9%」
- **SLA（服務水準協議）**：**對客戶的合約承諾**，未達成要賠償，例如「低於 99.5% 退還 10% 費用」

關係：用 SLI 衡量是否達到 SLO；SLO 通常訂得比 SLA 嚴格，保留緩衝。SLO 與實際表現的差距就是**錯誤預算**。

### Q4. 線上發生事故，你的處理步驟？

1. **確認與評估**：影響範圍多大、多嚴重，決定事故等級，必要時召集相關人員
2. **止血優先**：先恢復服務——回滾、切換流量、擴容、關閉問題功能、降級——**而不是先找根因**
3. **溝通**：指定一人負責定期更新狀態給團隊、客服與受影響使用者
4. **保留證據**：日誌、指標、時間軸，方便事後分析
5. **確認恢復**：監控指標回到正常
6. **事後檢討**：無究責的 Postmortem，找出根因與改善行動（補監控、補測試、改流程），並追蹤完成

### Q5. 什麼是 RPO 與 RTO？

- **RPO（復原點目標）**：最多可以接受**遺失多久的資料**。例如 RPO = 1 小時，代表至少每小時備份一次，或使用持續複寫。
- **RTO（復原時間目標）**：最多可以接受**停機多久**才恢復服務。例如 RTO = 4 小時。

數字越小，成本越高：RPO 接近 0 需要即時複寫；RTO 接近 0 需要熱備援或多活架構。應依業務重要性訂定，並**定期演練**驗證做得到。

### Q6. 如何避免告警太多沒人理？

- **針對症狀告警**：告警應代表「使用者受影響」（錯誤率上升、延遲超標），而非單純「CPU 80%」
- **每則告警都要可行動**：收到後知道要做什麼，最好附上 Runbook 連結；不需要人處理的改成儀表板或報表
- **分級**：緊急（立即通知值班）與一般（上班時間處理）分開
- **設定持續時間與門檻**：例如「持續 5 分鐘超過門檻」才告警，避免短暫抖動
- **合併與去重**：同一事件只通知一次
- **定期檢視**：刪除或調整誤報多、沒人處理的告警
- 以 **SLO 與錯誤預算的消耗速度**作為告警依據

## 過時技術（知道就好）

- **Nagios、Zabbix**：傳統主機監控，仍見於傳統機房；雲原生環境以 Prometheus 為主。
- **登入每台主機查看日誌檔**：無法應付多台伺服器與容器，已由集中式日誌取代。

## 本章回顧

- Logs 看細節、Metrics 看趨勢、Traces 看路徑
- 用 SLO 與錯誤預算平衡速度與穩定
- 出事先止血，事後不究責地檢討
