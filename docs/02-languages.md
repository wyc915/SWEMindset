# 02. 程式語言版圖與選型

> **一句話**：沒有最好的語言，只有最適合場景的語言。重點是知道每個語言「擅長什麼、代價是什麼」。

---

## 1. 主流語言定位 🟢

| 語言 | 最擅長 | 為什麼 | 代價 |
|---|---|---|---|
| **C** | 韌體、驅動、作業系統 | 最貼近硬體、資源最省 | 記憶體錯誤全靠自己避免 |
| **C++** | 遊戲引擎、高效能系統、嵌入式 | 效能頂尖又有高階抽象 | 複雜、易寫出難維護的程式 |
| **Rust** | 系統程式、基礎設施、嵌入式（成長中） | 編譯期就擋掉記憶體錯誤，效能近 C | 學習曲線陡 |
| **Go** | 雲端服務、微服務、DevOps 工具 | 簡單、併發好寫、編譯成單一檔案好部署 | 語言表達力較弱 |
| **C# / .NET** | 企業系統、Web API、Windows 桌面、Unity 遊戲 | 工具與框架完整，效能佳，已跨平台 | 舊版 .NET Framework 包袱 |
| **Java / Kotlin** | 企業後端、Android、大數據 | 生態最成熟、人才多 | 較耗記憶體；Android 首選 Kotlin |
| **TypeScript / JavaScript** | 前端、Node.js 後端、全端 | 瀏覽器唯一原生語言，生態最大 | JS 型別鬆散 → 用 TS 補強 |
| **Python** | AI/ML、資料分析、自動化腳本 | 寫得快、AI 函式庫壟斷 | 執行慢，不適合高效能核心 |
| **SQL** | 資料查詢 | 所有關聯式資料庫通用 | 各家語法略有差異 |

**快速對照**：
- 做 AI → Python
- 做韌體 → C（Rust 成長中）
- 做雲原生工具 → Go
- 做企業後端 → C# / Java
- 做網頁 → TypeScript

## 2. 影響選型的核心概念 🟡

### 2.1 編譯 vs 直譯

- **編譯成機器碼**（C、C++、Rust、Go）：執行快，需針對平台編譯。
- **編譯成中間碼 + JIT**（C#、Java）：執行時再轉成機器碼，兼顧跨平台與效能。現在也支援 AOT（預先編譯），啟動更快、適合容器。
- **直譯**（Python、JS 原始概念）：開發快，執行相對慢（現代 JS 引擎有 JIT，已很快）。

### 2.2 靜態型別 vs 動態型別

- **靜態**（C#、Java、TS、Go）：編譯時就抓錯，大型專案好維護、IDE 提示強。
- **動態**（Python、JS）：寫起來快，但錯誤延到執行時才爆。
- 趨勢：動態語言也在加型別（TypeScript、Python Type Hints）。

### 2.3 記憶體管理方式

| 方式 | 語言 | 特性 |
|---|---|---|
| 手動 | C | 最可控，最容易出錯 |
| RAII（離開範圍自動釋放） | C++ | 可控且較安全 |
| 所有權（Ownership） | Rust | 編譯器強制安全，無 GC |
| GC 自動回收 | C#、Java、Go、JS、Python | 開發輕鬆，偶有暫停 |

> 這也是韌體偏好 C/C++/Rust 的原因：**時間要可預測，不能被 GC 暫停打斷**。

### 2.4 併發模型

- **執行緒 + 鎖**：傳統做法（Java、C#）
- **async/await**：I/O 等待不佔執行緒（C#、JS、Python、Rust）
- **Goroutine + Channel**：Go 的招牌，「用溝通取代共享記憶體」

## 3. 選型原則 🔴

1. **團隊熟悉度**通常比語言本身優劣更重要
2. **生態系**：有沒有成熟的框架、函式庫、雲端支援
3. **非功能需求**：延遲、記憶體、啟動時間、硬體限制
4. **招募與長期維護**：冷門語言找不到人

- **.NET Framework**：僅維護，新專案用 .NET（8 以上）。
- **Python 2、AngularJS（1.x）、jQuery**：新專案不採用；jQuery 仍常見於舊系統。

## 本章回顧

- 先看場景再選語言
- 編譯方式、型別系統、記憶體管理、併發模型 = 語言的四個關鍵差異
