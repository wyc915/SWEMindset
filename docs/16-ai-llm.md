# 16. AI 輔助開發與 LLM 應用

> **一句話**：AI 已經是工程師的日常工具，也是產品的常見功能。要會「用 AI 開發」，也要懂「把 AI 做進產品」的基本架構。

---

## 1. 用 AI 輔助開發 🟢

**常見工具**：Claude Code、GitHub Copilot、Cursor 等 AI 程式助理與 Agent。

**有效用法**：
- 給足上下文：需求、限制、現有架構、範例
- 要求**先說明規劃，再產生程式**
- 讓 AI 寫測試、解釋舊程式、產生文件、找 bug
- **一律自己審查與測試**：AI 會自信地寫出錯誤程式或不存在的 API

**風險**：
- 把公司機密或客戶資料貼到未經核准的服務
- 產生帶有安全漏洞的程式
- 過度依賴，自己不理解程式碼 → 面試與除錯時露餡

## 2. 大型語言模型（LLM）基本觀念 🟢

| 觀念 | 白話 |
|---|---|
| **Token** | 模型處理文字的單位，計費與長度限制都以 Token 計算 |
| **Context Window** | 模型一次能「看到」的內容長度上限 |
| **幻覺（Hallucination）** | 模型自信地編造錯誤資訊 |
| **Prompt** | 給模型的指示，清楚的角色、任務、範例、輸出格式能大幅提升品質 |

## 3. 把 AI 做進產品：常見架構 🟡

### 3.1 RAG（檢索增強生成）—— 最常見

**問題**：模型不知道你公司的內部文件，且可能過時或幻覺。

**做法**：
```
1. 事前：把文件切成小段 → 轉成向量（Embedding）→ 存入向量資料庫
2. 使用者提問 → 找出最相關的幾段文件
3. 把「問題 + 相關文件」一起交給模型回答
```

→ 讓回答有根據、可附上來源。**這也是本知識庫未來平台化最可能用到的架構。**

### 3.2 Tool Use（工具呼叫）

讓模型決定要呼叫哪個 API（查天氣、查訂單），由你的程式實際執行並把結果回傳給模型。

### 3.3 Agent（代理）

模型自主規劃步驟、反覆呼叫工具，直到完成任務。能力強，但需要權限控管與人工確認關鍵操作。

### 3.4 MCP（Model Context Protocol）

連接 AI 應用與外部工具 / 資料來源的開放標準。概念類似「AI 界的 USB 接口」：工具寫一次 MCP Server，各種 AI 應用都能接。

## 4. 上線 AI 功能要注意 🟡

| 面向 | 重點 |
|---|---|
| **評估（Evals）** | 準備測試題組，量化回答品質 —— AI 功能的「單元測試」 |
| **成本** | 依 Token 計費；用快取、選擇適當大小的模型控制成本 |
| **延遲** | 用串流（SSE）逐字輸出，改善使用者體感 |
| **安全** | **Prompt Injection**：使用者或文件內容中夾帶惡意指令，誘使模型做不該做的事 → 限制權限、驗證輸出 |
| **隱私** | 留意傳送給模型的資料是否含個資 |

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. 什麼是 RAG？為什麼需要它？

**RAG（檢索增強生成）**：回答前先從知識庫**檢索相關資料**，再把資料與問題一起交給 LLM 生成答案。

流程：文件切塊 → 轉成向量存入向量資料庫 → 使用者提問時找出最相關的段落 → 組成提示詞交給模型。

需要它的原因：
- 模型**不知道私有資料**（公司文件、產品資訊）
- 模型的知識有**截止日期**
- **降低幻覺**：回答有依據，且可附上來源
- 比微調（Fine-tuning）**便宜、更新容易**：資料更新只需重新建立索引

### Q2. 如何降低 LLM 的幻覺？

- **提供依據**：使用 RAG 給模型相關資料，並要求「只根據提供的資料回答」
- **允許說不知道**：在提示中明確指示資料不足時回答不知道
- **要求引用來源**，方便驗證
- **清楚的提示詞**：明確任務、限制、輸出格式，並提供範例
- **結構化輸出與驗證**：要求 JSON 格式，再由程式檢查欄位與數值合理性
- **工具呼叫**：計算、查詢即時資料交給程式或 API，不讓模型自己編
- **評估（Evals）**：建立測試集持續量測正確率
- 關鍵決策保留**人工審核**

### Q3. 什麼是 Prompt Injection？如何防範？

**Prompt Injection**：攻擊者在使用者輸入、網頁、文件或郵件中**夾帶指令**，誘使模型忽略原本的規則，例如洩漏系統提示、存取不該存取的資料、或呼叫工具做出危險操作。

防範（沒有單一解法，需多層防禦）：
- **最小權限**：模型能呼叫的工具與資料權限越少越好
- **關鍵操作需人工確認**：付款、刪除、寄信等
- **區隔指令與資料**：外部內容標示為不可信資料，不當作指令
- **驗證輸出**：由程式檢查模型的輸出與工具呼叫參數
- **權限檢查放在後端程式**，不依賴模型判斷使用者能否存取
- 監控與記錄異常行為

### Q4. 你平常如何使用 AI 工具開發？如何確保品質？

回答範例：
- **使用情境**：產生樣板程式碼與測試、解釋不熟悉的舊程式、撰寫文件、協助除錯與重構、快速學習新技術
- **用法**：提供清楚的需求與上下文，先請 AI 說明規劃再產生程式，大任務拆成小步驟
- **確保品質**：
  - **逐行審查**，不理解的程式不合併
  - 一定要**跑測試**，並請 AI 補上測試案例
  - 核對官方文件，避免使用不存在或過時的 API
  - 用 Linter、SAST、Code Review 把關安全性
  - 遵守公司規範，不貼機密或客戶資料到未核准的服務

重點是展現「AI 加速我，但我對結果負責」。

### Q5. 如何評估一個 AI 功能的好壞？

- **建立評估資料集（Evals）**：準備具代表性的問題與預期答案或評分標準，包含邊界與刁鑽案例
- **定義指標**：
  - 正確性、完整性、是否引用正確來源（RAG 還要看檢索命中率）
  - 格式正確率、拒答是否恰當
  - 安全性：是否被 Prompt Injection 誘導
- **評分方式**：程式自動比對、LLM 評審（LLM-as-a-judge）、人工抽樣審查
- **非功能指標**：延遲、每次請求成本
- **線上指標**：使用者回饋（讚 / 倒讚）、任務完成率
- 每次修改提示詞或更換模型都**重新跑評估**，避免品質退化
