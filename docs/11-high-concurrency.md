# 11. 高併發與效能

> **一句話**：高併發的本質是「讓資料庫少做事」與「壞掉時不要連環崩潰」。

---

## 1. 衡量效能的指標 🟢

| 指標 | 意思 |
|---|---|
| **QPS / TPS** | 每秒處理的請求數 / 交易數 |
| **延遲（Latency）** | 單一請求花多久 |
| **P99 延遲** | 99% 的請求都比這個快。**看 P99 而不是平均值**，因為平均值會掩蓋少數極慢的請求 |
| **錯誤率** | 失敗請求的比例 |

> **原則：先量測，再優化。** 憑感覺優化常常改錯地方。

## 2. 擴展的兩種方式 🟢

- **垂直擴展（Scale Up）**：換更強的機器。簡單，但有上限且昂貴。
- **水平擴展（Scale Out）**：加更多機器。理論上無上限，但**服務必須無狀態**。

**無狀態**：伺服器不在記憶體中保存使用者資料（例如 Session），改放 Redis 或用 Token。這樣任何一台機器都能處理任何請求。

## 3. 負載平衡 🟢

把請求分散到多台伺服器。

- 常見演算法：**輪詢**（依序分配）、**最少連線**（給最閒的）、**雜湊**（同一使用者固定到同一台）
- 必須搭配**健康檢查**：自動移除壞掉的伺服器
- 工具：Nginx、雲端負載平衡器、K8s Service

## 4. 典型的高併發架構分層 🟡

```
使用者 → CDN（靜態資源）→ 負載平衡 → API 閘道（限流）
      → 無狀態應用伺服器（多台）→ Redis 快取 → MQ（削峰）→ 資料庫（讀寫分離）
```

每一層都在**擋掉流量**，讓最後到達資料庫的請求越少越好。

## 5. 韌性設計：防止連環崩潰 🟡

**雪崩效應**：服務 C 變慢 → 呼叫它的 B 執行緒全卡住 → 呼叫 B 的 A 也卡住 → 整個系統癱瘓。

| 手段 | 白話 | 比喻 |
|---|---|---|
| **逾時** | 等太久就放棄 | 所有外部呼叫都必須設定 |
| **重試 + 指數退避** | 失敗後等 1、2、4 秒再試，並加隨機延遲 | 避免大家同時重試再次打爆 |
| **熔斷（Circuit Breaker）** | 下游錯誤率過高就暫時不呼叫，直接回傳失敗，過一陣子再試探 | 家裡的電源保險絲 |
| **限流（Rate Limiting）** | 超過容量的請求直接拒絕（回傳 429） | 遊樂園入場人數管制 |
| **降級** | 犧牲非核心功能保核心，例如大促時暫停推薦功能 | 停電時只保留緊急照明 |
| **隔艙（Bulkhead）** | 不同功能用不同資源池，一個壞了不影響其他 | 船艙分隔，一艙進水不會沉船 |

- .NET 工具：**Polly**（內建於 `Microsoft.Extensions.Resilience`）
- 常見限流演算法：**Token Bucket（令牌桶）**——固定速率產生令牌，拿到令牌才能處理，允許短暫突發流量

## 6. 經典場景：秒殺 / 搶購（面試熱門）🔴

**問題**：10 萬人同時搶 100 件商品，資料庫會被打爆，還可能超賣。

**解法層層過濾**：
1. **前端**：按鈕防重複點擊、驗證碼
2. **閘道**：限流，同一使用者限制頻率
3. **Redis 預扣庫存**：庫存先載入 Redis，用原子遞減判斷是否搶到（擋掉 99.9% 請求）
4. **MQ 非同步下單**：搶到的人送入佇列，訂單服務照自己速度建立訂單
5. **資料庫最後防線**：`UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`，保證不超賣

## 7. 常見效能瓶頸與排查 🟡

| 瓶頸 | 症狀 | 常見原因 |
|---|---|---|
| 資料庫 | 查詢慢 | 缺索引、N+1、鎖競爭 |
| CPU | 使用率滿載 | 運算密集、無窮迴圈、序列化過重 |
| 記憶體 | 持續上升、頻繁 GC | 記憶體洩漏、大物件 |
| 執行緒 | 回應變慢但 CPU 不高 | 同步阻塞呼叫（例如 async 方法中使用 `.Result`）、連線池耗盡 |
| 網路 | 延遲高 | 呼叫次數太多、資料量太大 |

- 工具：APM（Application Insights、Datadog）、Profiler、壓力測試（k6、JMeter）

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. 如何設計一個秒殺系統？

核心思路：**層層過濾流量，讓到達資料庫的請求越少越好**。
1. **前端**：活動前頁面靜態化放 CDN、按鈕防重複點擊、加驗證碼分散請求時間
2. **閘道限流**：限制每個使用者與整體的請求頻率，超過直接回應「活動太熱門」
3. **Redis 預扣庫存**：活動前把庫存載入 Redis，以原子遞減（DECR 或 Lua 腳本）判斷是否搶到，沒搶到立刻回應
4. **MQ 非同步下單**：搶到的請求送入佇列，訂單服務依自身能力建立訂單，前端輪詢結果
5. **資料庫最後防線**：條件更新防超賣
6. **隔離**：秒殺服務獨立部署，避免影響主站

另外要考慮：一人限購（Redis Set 記錄已購者）、未付款訂單逾時釋放庫存。

### Q2. 如何防止超賣？

多層防護：
- **資料庫條件更新**（最根本）：`UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0`，影響 0 筆就代表賣完。這是原子操作，不會超賣。
- **樂觀鎖**：以版本號更新，衝突時重試
- **悲觀鎖**：`SELECT ... FOR UPDATE` 鎖住該列再扣減（併發低時可用）
- **Redis 原子遞減**：高併發時先在 Redis 判斷，結果小於 0 就回補並拒絕

錯誤做法：先查詢庫存、在程式判斷大於 0、再更新——查詢與更新之間其他請求會插隊，造成超賣。

### Q3. 什麼是熔斷？和限流有什麼不同？

- **熔斷（Circuit Breaker）**：保護**自己**不被**下游故障**拖垮。當呼叫下游的錯誤率或逾時過高時，熔斷器「跳開」，之後的請求直接失敗或回傳降級結果，不再呼叫下游；一段時間後放少量請求試探，恢復正常才關閉熔斷。
  - 三種狀態：關閉（正常）→ 開啟（直接失敗）→ 半開（試探）
- **限流（Rate Limiting）**：保護**自己**不被**上游過多請求**壓垮，超過容量就拒絕（回應 429）。

簡記：熔斷看「**下游健不健康**」，限流看「**進來的量多不多**」。兩者常一起使用。

### Q4. 為什麼服務要無狀態？

**無狀態**：伺服器不在本機記憶體保存使用者相關狀態（如 Session、上傳暫存檔），狀態改放在 Redis、資料庫、物件儲存，或由 Token 攜帶。

好處：
- **水平擴展**：任何一台機器都能處理任何請求，加機器就能提升容量
- **負載平衡簡單**：不需要黏性會話
- **容錯**：某台機器掛掉，使用者不會被登出或遺失資料
- **部署方便**：滾動更新、自動擴縮時可隨意新增或移除實例

這也是容器與 K8s 能自動調度的前提。

### Q5. 為什麼看 P99 而不是平均延遲？

平均值會**掩蓋少數極慢的請求**。例如 99 個請求 10ms、1 個請求 5 秒，平均約 60ms 看起來很好，但有 1% 使用者等了 5 秒。

P99 代表「99% 的請求都比這個值快」，能反映**最慢那群使用者的真實體驗**。而且：
- 一個頁面常呼叫多個 API，**任一個慢，整頁就慢**，實際使用者遇到長尾延遲的機率遠高於 1%
- 慢請求常是系統問題的早期訊號（GC、鎖競爭、連線池不足）

實務會同時看 P50（一般體驗）、P95、P99。

### Q6. 系統突然變慢，你的排查步驟？

1. **確認範圍**：全部變慢還是特定 API？所有使用者還是部分？從什麼時間開始？
2. **查最近變更**：是否剛部署、改設定、資料量暴增或有活動流量？若剛部署，先考慮**回滾止血**
3. **看監控指標**：流量、錯誤率、P99 延遲、CPU、記憶體、GC、執行緒池、連線池
4. **看分散式追蹤**：慢在哪一段——資料庫、外部 API、還是程式本身
5. **看資料庫**：慢查詢日誌、鎖等待、執行計畫是否改變
6. **看相依服務**：Redis、MQ、第三方 API 是否異常
7. **找到根因後修正**，並補上監控與告警，事後寫檢討

回答重點：**先止血再找根因**，用數據定位而不是猜測。

## 過時技術（知道就好）

- **Sticky Session（黏性會話）**：同一使用者固定導到同一台伺服器以保留記憶體 Session，妨礙水平擴展，現多改為無狀態設計。
- **Hystrix**：Netflix 的熔斷函式庫，已停止開發，Java 改用 Resilience4j。

## 本章回顧

- 層層擋流量：CDN → 限流 → 快取 → MQ → 資料庫
- 防雪崩：逾時、重試、熔斷、限流、降級
- 先量測（P99），再優化
