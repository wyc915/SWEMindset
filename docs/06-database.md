# 06. 資料庫

> **一句話**：資料是公司最重要的資產。程式寫錯可以重新部署，資料壞掉往往無法挽回。

## 學習目標

- 說明 ACID、四種隔離等級與各自的異常現象
- 選擇樂觀鎖或悲觀鎖，並解釋 MVCC 的作用
- 用執行計畫判斷索引是否生效，並避免 N+1 查詢
- 說出讀寫分離、分區、分片解決的問題與代價

---

## 1. SQL vs NoSQL 🟢

| | 關聯式（SQL） | NoSQL |
|---|---|---|
| 代表 | PostgreSQL、MSSQL、MySQL/MariaDB | MongoDB（文件）、Redis（鍵值）、Cassandra（寬欄） |
| 結構 | 固定 Schema、表格關聯 | 彈性結構 |
| 強項 | 交易、一致性、複雜查詢 | 水平擴展、高寫入量、結構多變 |
| 預設選擇 | **多數業務系統的首選** | 有明確需求再用 |

其他常見類型：
- **Elasticsearch**：全文搜尋、日誌分析
- **時間序列資料庫**（InfluxDB、TimescaleDB）：監控數據、IoT 感測資料
- **向量資料庫**（pgvector、Qdrant）：AI 語意搜尋

## 2. 交易與 ACID 🟢

**交易**：一組操作要嘛全成功、要嘛全失敗。例：轉帳要同時扣款與入帳。

| ACID | 意思 |
|---|---|
| Atomicity 原子性 | 全做或全不做 |
| Consistency 一致性 | 資料始終符合規則（例如餘額不為負） |
| Isolation 隔離性 | 同時執行的交易互不干擾 |
| Durability 持久性 | 提交後就算當機也不會遺失 |

## 3. 隔離等級（面試必考）🟡

同時有多筆交易時可能出現的問題：
- **髒讀**：讀到別人還沒提交的資料
- **不可重複讀**：同一交易內讀兩次，值被別人改了
- **幻讀**：同一交易內查兩次，多出（或少了）幾筆

| 隔離等級 | 防髒讀 | 防不可重複讀 | 防幻讀 |
|---|---|---|---|
| Read Uncommitted | ✘ | ✘ | ✘ |
| **Read Committed**（PG、MSSQL 預設） | ✔ | ✘ | ✘ |
| **Repeatable Read**（MySQL 預設） | ✔ | ✔ | 部分 |
| Serializable | ✔ | ✔ | ✔ |

> 越嚴格越安全，但併發效能越差。

## 4. 鎖：樂觀 vs 悲觀 🟡

- **悲觀鎖**：先鎖再改（`SELECT ... FOR UPDATE`）。衝突多時用，例如庫存扣減。
- **樂觀鎖**：不鎖，更新時檢查版本號是否變過，變了就重試。衝突少時用，效能好。
- **MVCC**：PostgreSQL、MySQL 透過保留多個資料版本，讓「讀不擋寫、寫不擋讀」。

## 5. 索引 🟡

**索引像書的目錄**：不用一頁頁翻（全表掃描），直接跳到目標。

- 主流結構：**B-Tree**，支援等值與範圍查詢
- **複合索引**遵守「最左前綴」：索引 (A, B) 可加速 `WHERE A=?` 與 `WHERE A=? AND B=?`，但不能加速只查 `B`
- **叢集索引**：資料本身按此排序（一張表只能一個，通常是主鍵）
- **代價**：加速查詢，但拖慢寫入、佔空間 → 不要每個欄位都建
- **常見失效**：對欄位做函式運算、`LIKE '%xx'`、隱式型別轉換
- 用 **執行計畫（EXPLAIN）** 確認是否真的走索引

## 6. ORM 與 N+1 問題 🟡

- **ORM**（EF Core、Hibernate、Prisma）：用物件操作資料庫，開發快
- **N+1 問題**：查 1 次訂單清單，再對每筆訂單各查 1 次明細 → 共 N+1 次查詢
- 解法：一次載入關聯資料（EF Core 的 `Include`、JOIN）

## 7. 正規化 vs 反正規化 🟢

- **正規化**：資料不重複存，避免更新不一致（標準做法）
- **反正規化**：刻意重複存，減少 JOIN 換取查詢速度（報表、高流量讀取）

## 8. 擴展與高可用 🟡→🔴

| 手段 | 解決什麼 |
|---|---|
| **連線池** | 建立連線很貴，重複使用已開好的連線 |
| **讀寫分離 / 主從複寫** | 讀多寫少時，讀取分散到從庫（注意複寫延遲） |
| **分區（Partition）** | 單一大表依日期等切塊，仍在同一資料庫 |
| **分片（Sharding）** | 資料分散到多台資料庫，突破單機上限（複雜度高，最後手段） |
| **自動容錯切換（Failover）** | 主庫掛掉時從庫接手 |

**資料庫遷移（Migration）**：Schema 變更要版本化（EF Core Migrations、Flyway），且要**向後相容**：先加新欄位 → 程式改用新欄位 → 最後才刪舊欄位。

## 9. PostgreSQL vs MSSQL vs MariaDB 🟡

| | PostgreSQL | MSSQL | MariaDB / MySQL |
|---|---|---|---|
| 授權 | 開源免費 | 商業授權 | 開源 |
| 強項 | 功能最完整、擴充強（JSONB、pgvector、PostGIS） | 與 Windows / .NET 整合、管理工具完善 | 簡單、Web 普及 |
| 定位 | **新專案最常見的首選** | 企業 Windows 環境 | 傳統網站 |

## 動手練習

1. **看執行計畫**：在 PostgreSQL 建立百萬筆測試資料，用 `EXPLAIN ANALYZE` 比較加索引前後的查詢；再故意寫出讓索引失效的條件觀察差異。
2. **重現隔離等級異常**：開兩個資料庫連線視窗，在不同隔離等級下手動交錯執行交易，觀察不可重複讀與幻讀。
3. **抓 N+1**：在 EF Core 開啟 SQL 日誌，寫一個迴圈讀取關聯資料的查詢，觀察產生的 SQL 數量，再用 `Include` 修正。

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. 說明 ACID 與四種隔離等級

**ACID**：原子性（全做或全不做）、一致性（資料始終符合規則）、隔離性（併發交易互不干擾）、持久性（提交後不遺失）。

**隔離等級**（由寬到嚴）：
- **Read Uncommitted**：可能讀到未提交資料（髒讀）
- **Read Committed**：只讀已提交資料，但同一交易內重讀可能不同（不可重複讀）——PostgreSQL、MSSQL 預設
- **Repeatable Read**：同一交易內重讀結果相同，但範圍查詢可能多出新資料（幻讀）——MySQL 預設，InnoDB 透過 MVCC 與間隙鎖大幅避免幻讀
- **Serializable**：結果等同依序執行，最安全但併發效能最差

越嚴格越安全、效能越差，實務多用預設等級，針對特定交易再提高或加鎖。

### Q2. 樂觀鎖與悲觀鎖的差別與使用時機

- **悲觀鎖**：假設一定會衝突，**讀取時就上鎖**（`SELECT ... FOR UPDATE`），其他交易必須等待
  - 適合：**衝突頻繁**、不能失敗重來的場景，例如熱門商品扣庫存
- **樂觀鎖**：假設很少衝突，**不上鎖**，更新時檢查版本號：`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?`，影響 0 筆代表被別人改過，需重試或提示使用者
  - 適合：**衝突少、讀多寫少**的場景，例如編輯個人資料、後台表單

EF Core 可用 `[Timestamp]` / RowVersion 或 Concurrency Token 實作樂觀鎖。

### Q3. 索引為什麼能加速？什麼情況索引會失效？

**為什麼快**：索引通常是 **B-Tree** 結構，資料已排序，查詢時像查字典目錄，只需走過少數幾層節點就能定位，不必掃描整張表（從 O(n) 降到約 O(log n)）。

**常見失效情況**：
- 對欄位做函式或運算：`WHERE YEAR(created_at) = 2026`（改寫成範圍查詢）
- 前置萬用字元：`LIKE '%abc'`
- **隱式型別轉換**：欄位是字串卻用數字比對
- 複合索引**沒用到最左欄位**
- 使用 `OR` 連接沒有索引的欄位
- 資料分布不均、選擇性太低（例如性別欄位），優化器判斷全表掃描更快

確認方式：查看**執行計畫**是否為 Index Seek / Index Scan。

### Q4. 什麼是 N+1 問題？

先用 1 次查詢取得 N 筆主資料，再對**每一筆**各發 1 次查詢取得關聯資料，總共 N+1 次查詢。例如：查 100 筆訂單，再逐筆查每筆訂單的明細 → 101 次查詢，資料量大時極慢。

常見於 ORM 的延遲載入（Lazy Loading）。

解法：
- **預先載入**：EF Core `Include()`、JOIN 一次取回
- **批次查詢**：先收集所有訂單 ID，用 `WHERE order_id IN (...)` 一次查明細
- 開發時開啟 SQL 日誌，觀察是否有大量重複查詢

### Q5. 什麼時候會選 NoSQL？

預設選關聯式資料庫，以下情況才考慮 NoSQL：
- **資料結構多變或高度巢狀**：例如商品屬性差異極大 → 文件資料庫（MongoDB）；不過 PostgreSQL 的 JSONB 也能處理很多這類需求
- **極高寫入量、需要水平擴展**：例如大量事件或感測器資料 → Cassandra、時間序列資料庫
- **簡單鍵值存取、要求極低延遲**：快取、Session → Redis
- **特殊查詢需求**：全文搜尋 → Elasticsearch；關係網路 → 圖形資料庫

需要接受的代價：交易能力較弱、多為最終一致、JOIN 能力有限。

### Q6. 讀寫分離會帶來什麼問題？

主要問題是**複寫延遲**：主庫寫入後，資料同步到從庫需要時間，若立刻從從庫讀取，會**讀不到剛寫入的資料**。例如使用者剛改完暱稱，重新整理卻看到舊的。

解法：
- **寫後讀主庫**：寫入後一段時間內（或該使用者的關鍵讀取）強制讀主庫
- 對一致性要求高的查詢一律讀主庫
- 監控複寫延遲，延遲過大時暫時將讀取切回主庫

其他問題：架構與程式複雜度提高、需處理從庫故障切換。

## 過時技術（知道就好）

- **ADO.NET DataSet / DataTable 直接綁定 UI**：舊式寫法，現多用 ORM 或 Dapper。
- **大量商業邏輯寫在 Stored Procedure**：舊系統常見，難測試、難版控，新系統傾向放在應用層。

## 本章回顧

- 預設用關聯式資料庫，有明確理由再用 NoSQL
- 交易靠 ACID，併發靠隔離等級與鎖
- 慢查詢第一步：看執行計畫、檢查索引
