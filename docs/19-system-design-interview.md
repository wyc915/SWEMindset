# 19. 系統設計面試框架

> **一句話**：系統設計沒有標準答案，面試官看的是**你如何釐清需求、估算規模、做出取捨並說明理由**。這章把前面所有章節串起來。

---

## 1. 四步驟框架 🟡

### 步驟一：釐清需求（約 5 分鐘）

**不要一開始就畫架構圖。** 先問：

- **功能需求**：核心功能有哪些？這次範圍不做什麼？
- **非功能需求**：
  - 使用者規模？每日活躍使用者多少？
  - 讀多還是寫多？
  - 延遲要求？
  - 一致性要求？（錢相關 → 強一致；動態牆 → 最終一致）
  - 可用性要求？

### 步驟二：估算規模（約 5 分鐘）

粗估即可，目的是決定架構等級：

```
例：每日 1,000 萬活躍使用者，每人每天 10 次請求
→ 每日 1 億次請求
→ 平均 QPS ≈ 1 億 / 86,400 ≈ 1,200
→ 尖峰通常抓平均的 2～5 倍 ≈ 3,000～6,000 QPS
```

再估儲存空間：每筆資料大小 × 每日筆數 × 保存天數。

### 步驟三：高階架構設計（約 15 分鐘）

畫出主要元件與資料流：

```
用戶端 → CDN → 負載平衡 → API 閘道 → 應用服務
                                    ├→ 快取（Redis）
                                    ├→ 資料庫
                                    └→ 訊息佇列 → 背景處理服務
```

並定義：
- 核心 API（第 05 章）
- 資料模型與資料庫選擇（第 06 章）

### 步驟四：深入與取捨（約 15 分鐘）

挑出瓶頸深入討論：
- 單點故障在哪？怎麼做高可用？
- 資料庫撐不住怎麼辦？→ 快取、讀寫分離、分片
- 尖峰流量？→ MQ 削峰、限流
- 下游故障？→ 熔斷、降級
- 一致性怎麼保證？→ 交易、Saga、冪等

**每個選擇都說出取捨**：「我選 X，因為 Y，代價是 Z」。

## 2. 常用元件對照表 🟡

| 需求 | 解法 | 參考章節 |
|---|---|---|
| 讀多寫少、加速查詢 | Redis 快取 | 07 |
| 尖峰流量、非同步處理 | RabbitMQ / Kafka | 08 |
| 靜態檔、全球加速 | CDN | 01、04 |

| 防重複請求 | 冪等鍵 | 05 |

| 保護系統 | 限流、熔斷、降級 | 11 |
| 唯一 ID | UUID v7 / Snowflake | 10 |

## 3. 經典題目與關鍵點 🔴

| 題目 | 關鍵考點 |
|---|---|
| **短網址服務** | ID 產生與編碼、讀多寫少 → 快取、重新導向（301 vs 302） |
| **秒殺系統** | 限流、Redis 預扣庫存、MQ 非同步、防超賣（第 11 章） |
| **聊天系統** | WebSocket 長連線、訊息儲存、離線訊息、已讀狀態 |
| **動態牆（如社群貼文）** | 發文時推送到粉絲（寫擴散）vs 讀取時才拉取（讀擴散）、名人帳號特殊處理 |
| **通知系統** | MQ、多管道（簡訊、Email、推播）、重試、去重 |
| **限流器** | Token Bucket、分散式計數（Redis） |
| **IoT 資料收集平台** | MQTT、Kafka、時間序列資料庫、裝置管理（銜接第 17 章） |

## 4. 常見錯誤 🟢

- 沒問需求就開始畫圖
- 一開始就上微服務、Kafka、K8s 等複雜架構（**過度設計**）
- 只講用了什麼技術，沒講**為什麼**
- 忽略單點故障
- 不懂裝懂：說「這部分我不熟，我的理解是……」比亂講好

---

## 本章回顧

- 需求 → 估算 → 架構 → 深入取捨
- 從簡單架構開始，依瓶頸逐步演進
- 每個決策都說出理由與代價
