# 09. 軟體架構

> **一句話**：架構是「之後很難改的決定」。好的架構不是最潮的，而是讓團隊在現階段改得動、跑得穩。

---

## 1. 程式內部怎麼分層 🟢

### 1.1 三層架構（最基本）

```
展示層（Controller / UI） → 商業邏輯層（Service） → 資料存取層（Repository）
```

每層只呼叫下一層，職責清楚。多數 .NET / Java 專案從這裡開始。

### 1.2 Clean Architecture / 洋蔥架構 🟡

**核心思想：商業邏輯在中心，不依賴任何框架或資料庫。**

```
     外層：Web 框架、資料庫、外部 API（可替換）
        中層：應用服務（流程協調）
           核心：領域模型與商業規則（最穩定）
```

- 依賴方向**只能由外向內**
- 好處：換資料庫或框架時，核心邏輯不用改；核心可以不連資料庫就做單元測試
- 代價：檔案與介面變多，小專案可能過度設計

## 2. 系統怎麼部署：單體 vs 微服務 🟡

| 架構 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| **單體** | 整個系統一個專案、一起部署 | 簡單、好除錯、交易容易 | 變大後耦合嚴重，改一點要全部重新部署 |
| **模組化單體** | 一起部署，但內部依業務嚴格分模組 | 兼顧簡單與邊界清楚 | 需團隊紀律 |
| **微服務** | 依業務拆成多個獨立服務，各自部署、各自資料庫 | 獨立擴展、獨立部署、團隊自治 | 網路呼叫、資料一致性、維運複雜度大增 |
| **Serverless** | 只寫函式，由雲端負責執行與擴展 | 免管主機、依用量計費 | 冷啟動延遲、綁定雲廠商 |

### 業界共識

> **先做模組化單體，等遇到明確痛點（團隊太大互相卡住、某模組需要獨立擴展）再拆微服務。**

太早拆微服務 = 承擔分散式系統的所有複雜度，卻沒得到好處（俗稱「分散式單體」）。

**康威定律**：系統架構會長得像組織的溝通結構。微服務適合多個獨立團隊。

## 3. 領域驅動設計（DDD）🔴

**解決的問題：大型系統如何切分邊界？**

| 概念 | 白話 |
|---|---|
| **Bounded Context（界限上下文）** | 同一個詞在不同部門意思不同。例：「商品」在銷售是售價與描述，在倉儲是重量與庫位 → 應切成兩個模組 |
| **通用語言** | 開發者與業務人員用同一套詞彙 |
| **Aggregate（聚合）** | 一組必須一起保持一致的物件，例：訂單與訂單明細 |
| **Domain Event（領域事件）** | 業務上發生的事：「訂單已付款」 |

> 拆微服務時，Bounded Context 通常就是服務邊界。

## 4. 微服務常用配套模式 🔴

| 模式 | 解決什麼 |
|---|---|
| **API Gateway** | 統一入口：路由、認證、限流（Kong、YARP、雲端 API Gateway） |
| **BFF** | 為 Web、App 各自提供專屬的 API 聚合層 |
| **CQRS** | 讀寫分開設計：寫入重正確性，讀取可用專門優化的資料結構 |
| **Saga** | 跨服務的交易：每一步失敗時執行補償動作（例：扣款成功但出貨失敗 → 退款） |
| **Event Sourcing** | 儲存「發生過的事件」而非最終狀態，可完整追溯（如銀行帳本）——複雜度高，少數場景適用 |
| **Strangler Fig（絞殺者模式）** | 舊系統逐步替換：新功能做在新系統，舊功能一點一點搬 |

## 5. 架構就是取捨 🔴

常見的品質屬性：**可用性、效能、可擴展性、安全性、可維護性、成本**。它們常互相衝突（例如更高可用性 = 更高成本）。

**用 ADR（架構決策紀錄）記錄**：背景、考慮過的選項、最後決定、理由與代價。讓後人知道「為什麼這樣做」。

## 過時技術（知道就好）

- **SOA + ESB（企業服務匯流排）**：微服務的前身，所有整合集中在一個匯流排，容易成為瓶頸。
- **大型共用資料庫的多系統整合**：多個系統直接共用一個資料庫，耦合極高，微服務強調「各自擁有資料」。

## 本章回顧

- 程式內部：依賴朝向商業核心
- 系統層級：先模組化單體，痛了再拆
- 邊界依業務切（DDD），不是依技術切
