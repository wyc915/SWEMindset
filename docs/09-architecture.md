# 09. 軟體架構

> **一句話**：架構是「之後很難改的決定」。好的架構不是最潮的，而是讓團隊在現階段改得動、跑得穩。

## 學習目標

- 說明分層架構與 Clean Architecture 的依賴規則
- 比較單體、模組化單體、微服務，並判斷拆分時機
- 用 DDD 的界限上下文切分服務邊界
- 說出 API Gateway、CQRS、Saga、絞殺者模式的用途

---

## 1. 程式內部怎麼分層 🟢

### 1.1 三層架構（最基本）

```
展示層（Controller / UI） → 商業邏輯層（Service） → 資料存取層（Repository）
```

每層只呼叫下一層，職責清楚。多數 .NET / Java 專案從這裡開始。

### 1.2 Clean Architecture / 洋蔥架構 🟡

**核心思想：商業邏輯在中心，不依賴任何框架或資料庫。**

```
     外層：Web 框架、資料庫、外部 API（可替換）
        中層：應用服務（流程協調）
           核心：領域模型與商業規則（最穩定）
```

- 依賴方向**只能由外向內**
- 好處：換資料庫或框架時，核心邏輯不用改；核心可以不連資料庫就做單元測試
- 代價：檔案與介面變多，小專案可能過度設計

## 2. 系統怎麼部署：單體 vs 微服務 🟡

| 架構 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| **單體** | 整個系統一個專案、一起部署 | 簡單、好除錯、交易容易 | 變大後耦合嚴重，改一點要全部重新部署 |
| **模組化單體** | 一起部署，但內部依業務嚴格分模組 | 兼顧簡單與邊界清楚 | 需團隊紀律 |
| **微服務** | 依業務拆成多個獨立服務，各自部署、各自資料庫 | 獨立擴展、獨立部署、團隊自治 | 網路呼叫、資料一致性、維運複雜度大增 |
| **Serverless** | 只寫函式，由雲端負責執行與擴展 | 免管主機、依用量計費 | 冷啟動延遲、綁定雲廠商 |

### 業界共識

> **先做模組化單體，等遇到明確痛點（團隊太大互相卡住、某模組需要獨立擴展）再拆微服務。**

太早拆微服務 = 承擔分散式系統的所有複雜度，卻沒得到好處（俗稱「分散式單體」）。

**康威定律**：系統架構會長得像組織的溝通結構。微服務適合多個獨立團隊。

## 3. 領域驅動設計（DDD）🔴

**解決的問題：大型系統如何切分邊界？**

| 概念 | 白話 |
|---|---|
| **Bounded Context（界限上下文）** | 同一個詞在不同部門意思不同。例：「商品」在銷售是售價與描述，在倉儲是重量與庫位 → 應切成兩個模組 |
| **通用語言** | 開發者與業務人員用同一套詞彙 |
| **Aggregate（聚合）** | 一組必須一起保持一致的物件，例：訂單與訂單明細 |
| **Domain Event（領域事件）** | 業務上發生的事：「訂單已付款」 |

> 拆微服務時，Bounded Context 通常就是服務邊界。

## 4. 微服務常用配套模式 🔴

| 模式 | 解決什麼 |
|---|---|
| **API Gateway** | 統一入口：路由、認證、限流（Kong、YARP、雲端 API Gateway） |
| **BFF** | 為 Web、App 各自提供專屬的 API 聚合層 |
| **CQRS** | 讀寫分開設計：寫入重正確性，讀取可用專門優化的資料結構 |
| **Saga** | 跨服務的交易：每一步失敗時執行補償動作（例：扣款成功但出貨失敗 → 退款） |
| **Event Sourcing** | 儲存「發生過的事件」而非最終狀態，可完整追溯（如銀行帳本）——複雜度高，少數場景適用 |
| **Strangler Fig（絞殺者模式）** | 舊系統逐步替換：新功能做在新系統，舊功能一點一點搬 |

## 5. 架構就是取捨 🔴

常見的品質屬性：**可用性、效能、可擴展性、安全性、可維護性、成本**。它們常互相衝突（例如更高可用性 = 更高成本）。

**用 ADR（架構決策紀錄）記錄**：背景、考慮過的選項、最後決定、理由與代價。讓後人知道「為什麼這樣做」。

## 動手練習

1. **畫出依賴圖**：替你目前的專案畫出模組依賴關係，找出循環依賴與違反分層的地方。
2. **模組化單體重構**：挑一個專案，依業務（如訂單、會員、商品）切成獨立模組，模組之間只透過公開介面或事件溝通。
3. **寫一份 ADR**：針對最近一個技術決策，寫下背景、選項、決定與代價。

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. 單體與微服務的優缺點？你會怎麼選？

| | 單體 | 微服務 |
|---|---|---|
| 優點 | 開發、測試、部署、除錯簡單；本地交易容易；效能好（無網路呼叫） | 獨立部署與擴展、技術可異質、團隊自治、故障隔離 |
| 缺點 | 規模變大後耦合嚴重、建置部署慢、無法局部擴展 | 分散式複雜度：網路失敗、資料一致性、維運與監控成本高 |

**怎麼選**：團隊小、業務還在變動 → 先做**模組化單體**；當團隊多到互相阻礙、某些模組需要獨立擴展或不同部署頻率時，再沿著業務邊界逐步拆出微服務。

### Q2. 什麼時候該拆微服務？要怎麼拆？

**該拆的訊號**：
- 多個團隊在同一份程式碼互相卡住、合併衝突頻繁
- 某模組需要**獨立擴展**（例如搜尋流量遠高於其他功能）
- 某模組需要**不同的發布頻率**或技術
- 某模組故障會拖垮整個系統，需要隔離

**怎麼拆**：
- 依**業務能力 / DDD 的 Bounded Context** 切分，而不是依技術分層（不要拆成「資料庫服務」）
- **每個服務擁有自己的資料**，不共用資料庫
- 先從邊界最清楚、耦合最低的模組開始，用**絞殺者模式**逐步搬遷
- 先把可觀測性、CI/CD、自動化部署準備好

### Q3. 微服務之間如何處理交易一致性？

微服務各有資料庫，無法用單一資料庫交易，主流做法是 **Saga**：把大交易拆成一連串本地交易，任一步失敗就執行前面步驟的**補償動作**。

例：下單 → 扣庫存 → 扣款。若扣款失敗，執行「回補庫存」、「取消訂單」。

兩種協調方式：
- **編排（Orchestration）**：由一個協調者依序呼叫各服務，流程清楚、好追蹤
- **協作（Choreography）**：各服務透過事件互相觸發，耦合低但流程分散

搭配 **Outbox** 確保事件可靠發出、消費者**冪等**。接受「最終一致」是前提。

### Q4. 說明 Clean Architecture 的依賴規則

**依賴只能由外向內**：
- 最內層是**領域模型與商業規則**，不依賴任何框架、資料庫或 UI
- 中層是**應用服務（Use Case）**，協調流程，只依賴內層
- 最外層是**基礎設施**：Web 框架、資料庫、外部 API

內層需要外部能力（例如存資料）時，**在內層定義介面**（如 `IOrderRepository`），由外層實作，再透過 DI 注入——這就是依賴反轉。

好處：商業邏輯可以不連資料庫就做單元測試，替換框架或資料庫時核心不用改。

### Q5. CQRS 是什麼？什麼情況適合？

**CQRS（命令查詢責任分離）**：把**寫入（Command）**與**讀取（Query）**分成不同模型，甚至不同資料儲存。
- 寫入端：著重商業規則與一致性
- 讀取端：針對畫面需求設計的查詢模型，可反正規化、使用快取或搜尋引擎

**適合**：
- 讀寫比例懸殊、讀取需求複雜（多種報表、搜尋、聚合）
- 讀寫需要獨立擴展
- 搭配事件驅動或 Event Sourcing

**不適合**：簡單 CRUD 系統——會增加複雜度並帶來讀寫之間的資料延遲。輕量做法是同一資料庫內，查詢直接用 Dapper / SQL，寫入走領域模型。

### Q6. 舊系統如何逐步重構？

使用**絞殺者模式（Strangler Fig）**，避免高風險的「整個重寫」：
1. **先補測試與監控**，確保能察覺行為改變
2. 在舊系統前放一層**路由（API Gateway / 反向代理）**
3. **新功能直接做在新系統**；舊功能挑邊界清楚的一塊重寫，路由逐步切過去
4. 新舊系統之間用**防腐層（Anti-Corruption Layer）**轉換資料模型，避免舊設計汙染新系統
5. 舊功能全部搬完後，移除舊系統

每一步都可獨立上線、可回滾，風險可控。

## 過時技術（知道就好）

- **SOA + ESB（企業服務匯流排）**：微服務的前身，所有整合集中在一個匯流排，容易成為瓶頸。
- **大型共用資料庫的多系統整合**：多個系統直接共用一個資料庫，耦合極高，微服務強調「各自擁有資料」。

## 本章回顧

- 程式內部：依賴朝向商業核心
- 系統層級：先模組化單體，痛了再拆
- 邊界依業務切（DDD），不是依技術切
