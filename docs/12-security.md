# 12. 資訊安全

> **一句話**：安全不是最後再加的功能，而是每一行程式的預設習慣。多數漏洞來自「相信了不該相信的輸入」。

---

## 1. 最常見的攻擊與防禦 🟢

| 攻擊 | 怎麼發生 | 防禦 |
|---|---|---|
| **SQL Injection** | 把使用者輸入直接拼接進 SQL | **參數化查詢**（ORM 預設就是），永不字串拼接 |
| **XSS 跨站腳本** | 使用者輸入的腳本被顯示在別人的頁面上執行 | 輸出跳脫（框架預設會做）、CSP 標頭 |
| **CSRF 跨站請求偽造** | 惡意網站利用你已登入的 Cookie 發送請求 | SameSite Cookie、CSRF Token |
| **權限失效（IDOR）** | 把網址 `/orders/123` 改成 `/orders/124` 就看到別人資料 | **每個請求都在後端檢查擁有權**，不能只靠前端隱藏 |
| **敏感資料外洩** | 密碼明碼、Log 印出個資、錯誤訊息洩漏內部資訊 | 加密、遮罩、統一錯誤訊息 |
| **SSRF** | 讓伺服器去請求攻擊者指定的內部網址 | 白名單限制可存取的目標 |

> **OWASP Top 10** 是業界最常引用的 Web 風險清單，2025 版第一名為「存取控制失效」。

## 2. 密碼與加密觀念 🟢

| 觀念 | 重點 |
|---|---|
| **雜湊 ≠ 加密** | 雜湊不可逆（存密碼用）；加密可解密（存需要還原的資料用） |
| **密碼儲存** | 用 **Argon2id / bcrypt / PBKDF2**（刻意設計成慢）+ Salt；**不要用 MD5、SHA-1，也不要直接用 SHA-256** |
| **對稱加密** | 同一把金鑰加解密，快（AES） |
| **非對稱加密** | 公鑰加密、私鑰解密，或私鑰簽章、公鑰驗證（RSA、ECC）；HTTPS 用它來交換對稱金鑰 |
| **數位簽章** | 證明「是我發的」且「沒被改過」，例：JWT、軟體更新、韌體驗證 |

## 3. 開發時的安全習慣 🟡

- **最小權限**：資料庫帳號、雲端權限、服務帳號只給必要的權限
- **機密不進 Git**：密碼、API Key 放在環境變數或機密管理服務（Azure Key Vault、AWS Secrets Manager、HashiCorp Vault）
- **全站 HTTPS**，使用 TLS 1.2 以上
- **輸入驗證在後端**：前端驗證只是使用者體驗，攻擊者可以直接呼叫 API
- **Log 不記錄敏感資料**：密碼、完整卡號、Token
- **相依套件定期更新**：多數漏洞來自第三方套件

## 4. 軟體供應鏈安全 🟡

近年最受重視的領域：攻擊者不打你，而是汙染你用的套件。

- **相依套件掃描（SCA）**：Dependabot、Snyk 自動通知有漏洞的套件
- **靜態程式碼掃描（SAST）**：在 CI 中自動找出常見漏洞寫法
- **機密掃描**：防止不小心把金鑰 commit 進去
- **容器映像掃描**：Trivy 等工具
- **SBOM（軟體物料清單）**：列出產品用了哪些元件，歐盟《網路韌性法案》（CRA）等法規逐步要求

## 5. 零信任（Zero Trust）🔴

傳統觀念：公司內網是安全的。
零信任：**不信任任何網路位置，每個請求都要驗證身分與權限**。服務之間也要認證（如 mTLS）。

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. 如何防止 SQL Injection？

- **使用參數化查詢**（最根本）：SQL 與參數分開傳給資料庫，使用者輸入永遠被當成資料，不會被當成指令。ORM（EF Core）與 Dapper 的參數寫法預設就是參數化。
- **絕不用字串拼接 SQL**，包含預存程序內的動態 SQL
- 無法參數化的部分（如排序欄位名稱）使用**白名單**
- 資料庫帳號**最小權限**，應用程式帳號不給刪表或系統管理權限
- 搭配 SAST 工具在 CI 中自動檢查

### Q2. XSS 和 CSRF 差在哪？

- **XSS**：攻擊者讓**惡意腳本在你的網站上執行**（例如在留言中植入腳本），受害者瀏覽時腳本會竊取 Cookie、Token 或冒用操作。
  - 防禦：輸出跳脫、避免直接插入未過濾的 HTML、CSP、HttpOnly Cookie
- **CSRF**：受害者已登入你的網站，**在惡意網站被誘導送出請求**，瀏覽器自動帶上 Cookie，伺服器誤以為是本人操作。
  - 防禦：SameSite Cookie、CSRF Token、敏感操作重新驗證

關鍵差異：XSS 利用網站對**使用者輸入**的信任；CSRF 利用網站對**使用者瀏覽器**的信任。若改用 Authorization 標頭帶 Token 而不依賴 Cookie，CSRF 風險會大幅降低。

### Q3. 密碼應該怎麼儲存？為什麼不能用 MD5？

**正確做法**：使用專為密碼設計的**慢速雜湊**演算法——**Argon2id**（首選）、bcrypt、PBKDF2，並為每個使用者加上**隨機 Salt**（這些演算法通常會自動處理 Salt）。驗證時用相同方式雜湊輸入的密碼再比對。

**為什麼不能用 MD5（或直接用 SHA-256）**：
- 這些演算法**設計得很快**，GPU 每秒可計算數十億次，暴力破解成本很低
- 沒加 Salt 時，可用**彩虹表**直接查出常見密碼
- MD5 本身也已存在碰撞攻擊

慢速雜湊刻意增加計算成本，讓暴力破解變得不切實際。

### Q4. 雜湊和加密的差別？

- **雜湊（Hash）**：單向、**不可逆**，相同輸入必定產生相同輸出，任意長度輸入產生固定長度輸出
  - 用途：儲存密碼、檢查檔案完整性、數位簽章的前置步驟
- **加密（Encryption）**：雙向、**可用金鑰解密**還原原文
  - 用途：保護之後還需要讀取的資料，例如傳輸內容、身分證字號、信用卡資料

判斷方法：之後需要拿回原始資料嗎？需要就用加密，不需要（只要比對）就用雜湊。

### Q5. 對稱與非對稱加密的差別？HTTPS 如何使用它們？

- **對稱加密**（AES）：加解密用**同一把金鑰**，速度快，但金鑰如何安全交給對方是問題
- **非對稱加密**（RSA、ECC）：一對**公鑰與私鑰**，公鑰可公開，速度慢

**HTTPS（TLS）結合兩者**：
1. 伺服器出示**憑證**（含公鑰，由 CA 簽章），瀏覽器驗證憑證可信
2. 雙方透過**非對稱方式的金鑰交換**（現行多為 ECDHE）協商出一把**對稱的工作階段金鑰**
3. 之後所有資料都用這把**對稱金鑰**快速加密傳輸

簡記：非對稱負責「安全地交換鑰匙」與「驗證身分」，對稱負責「大量資料加密」。

### Q6. API Key 和資料庫密碼要放在哪裡？

**不要**：寫在程式碼、提交到 Git 的設定檔、前端程式、日誌中。

**應該**：
- 開發環境：本機的使用者機密（.NET User Secrets）或未納入版控的 `.env`
- 正式環境：**機密管理服務**——Azure Key Vault、AWS Secrets Manager、HashiCorp Vault；K8s 使用 Secret（並啟用加密或搭配外部機密管理）
- 以**環境變數**或掛載方式注入應用程式
- 可行時改用**受控識別（Managed Identity）**，連密碼都不需要
- 定期**輪替**，並在 CI 啟用機密掃描，防止誤提交

若機密不慎提交到 Git，即使刪除提交紀錄也要**立即作廢並更換**。

## 過時技術（知道就好）

- **MD5、SHA-1、DES、3DES**：已不安全，不可用於密碼或簽章。
- **SSL、TLS 1.0 / 1.1**：已淘汰。
- **把密碼寫在 Web.config / appsettings.json 並提交到版控**：舊專案常見的壞習慣。

- 密碼用 Argon2id / bcrypt，機密不進 Git
