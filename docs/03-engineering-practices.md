# 03. 軟體工程實務

> **一句話**：會寫程式不等於會做軟體。版本控制、程式碼品質、測試，決定你的程式能不能被團隊長期維護。

---

## 1. Git 與分支策略 🟢

**必懂概念**：commit（存檔點）、branch（平行開發線）、merge（合併）、rebase（把提交接到最新基底上，歷史較乾淨）、PR / MR（請求審查後合併）。

| 策略 | 做法 | 適合 |
|---|---|---|
| **GitHub Flow** | main + 短期功能分支 + PR | 多數 Web 團隊，持續部署 |
| **Trunk-Based** | 極短分支、每天合併到 main，未完成功能用 Feature Flag 關閉 | 高頻部署團隊（業界主流方向） |
| **Git Flow** | main / develop / feature / release / hotfix | 有固定發版週期（如韌體、套裝軟體） |

**實用規範**：
- Commit 訊息：`feat:` 新功能、`fix:` 修 bug、`docs:` 文件（Conventional Commits）
- 版本號 **SemVer**：`主版號.次版號.修訂號`，破壞相容才升主版號

## 2. 程式碼品質原則 🟢

| 原則 | 白話解釋 |
|---|---|
| **單一職責** | 一個類別只做一件事，改動理由只有一個 |
| **開放封閉** | 加新功能時新增程式碼，而不是改舊程式碼 |
| **依賴反轉 / 依賴注入（DI）** | 依賴「介面」而不是具體實作，方便替換與測試（ASP.NET Core 內建 DI） |
| **DRY** | 同一個業務規則只寫在一個地方 |
| **KISS / YAGNI** | 保持簡單；現在不需要的功能不要做 |
| **高內聚、低耦合** | 相關的放一起，模組之間少牽扯 |
| **組合優於繼承** | 繼承太深會僵化，改用組合 |

> SOLID 的五個字母面試常考：單一職責、開放封閉、里氏替換、介面隔離、依賴反轉。

## 3. 設計模式：知道「解決什麼問題」即可 🟡

| 模式 | 解決的問題 | 生活例子 |
|---|---|---|
| **Factory** | 建立物件的邏輯集中管理 | 依參數產生不同付款方式物件 |
| **Singleton** | 全域只需一個實例 | 設定管理器（現多改用 DI 容器管理生命週期） |
| **Strategy** | 演算法可抽換 | 不同運費計算規則 |
| **Observer** | 狀態改變時通知訂閱者 | 事件、前端響應式資料 |
| **Adapter** | 讓不相容的介面能接起來 | 包裝第三方 API |
| **Decorator** | 不改原類別就加功能 | 加上日誌、快取 |
| **Repository** | 隔離資料存取邏輯 | 業務程式不直接寫 SQL |

## 4. 測試 🟢→🟡

**測試金字塔**：

```
      /  E2E  \        少量：模擬使用者操作，慢、易壞
     / 整合測試 \       適量：測模組與資料庫、API 的串接
    /  單元測試  \      大量：測單一函式邏輯，快、穩
```

- **Mock / Stub**：用假物件取代外部依賴（資料庫、第三方 API），讓單元測試只測自己。
- **TDD**：先寫測試再寫程式，逼你先想清楚需求。
- **覆蓋率不是目標**：重點是核心邏輯與邊界條件（空值、極大值、錯誤輸入）。
- 主流工具：xUnit（.NET）、Jest / Vitest（JS）、pytest、Playwright（E2E）。

## 5. 團隊協作 🟢

- **Code Review**：看正確性、可讀性、安全性；格式交給 Linter / Formatter 自動處理。
- **敏捷 / Scrum**：以 1～2 週為一個 Sprint，持續交付、定期回顧改進。
- **文件**：README（怎麼跑起來）、API 文件（OpenAPI）、ADR（為什麼這樣決定）。

## 面試常問

> 先試著自己回答，再對照參考解答。

### Q1. 說明 SOLID 原則，並舉一個你實際應用的例子

- **S 單一職責**：一個類別只有一個被修改的理由
- **O 開放封閉**：對擴充開放、對修改封閉
- **L 里氏替換**：子類別要能替換父類別而不破壞行為
- **I 介面隔離**：不強迫實作用不到的方法，介面要小而專一
- **D 依賴反轉**：高層模組依賴抽象，而非具體實作

舉例（開放封閉 + 依賴反轉）：付款功能定義 `IPaymentProvider` 介面，信用卡、Line Pay 各自實作。新增付款方式只要新增一個類別並註冊到 DI，不用修改既有的付款流程程式碼，也方便用假實作做單元測試。

### Q2. merge 和 rebase 的差別？

- **merge**：產生一個合併提交，**保留完整分支歷史**，安全但歷史線較雜亂
- **rebase**：把自己的提交「搬到」最新的基底上重新套用，**歷史是一直線**，較乾淨，但會**改寫提交紀錄**

原則：
- **已推送且他人共用的分支不要 rebase**，會讓別人的歷史對不上
- 個人功能分支同步主幹時可用 rebase，合併回主幹常用 merge 或 squash merge

### Q3. 什麼是依賴注入？好處是什麼？

**依賴注入（DI）**：類別不自己 `new` 它需要的物件，而是由外部（通常是 DI 容器）透過建構子傳入。

好處：
- **低耦合**：類別只依賴介面，可輕易替換實作（例如換資料庫、換寄信服務）
- **好測試**：單元測試時注入 Mock，不用真的連資料庫
- **集中管理生命週期**：Singleton、Scoped、Transient 由容器統一控管

ASP.NET Core 內建 DI 容器，在 `Program.cs` 註冊服務即可。

### Q4. 單元測試和整合測試的差別？什麼時候用 Mock？

- **單元測試**：測試單一函式或類別的邏輯，隔離所有外部依賴，**快速、穩定、數量多**
- **整合測試**：測試多個元件串接，例如程式與真實資料庫、API 一起運作，**較慢但更接近真實**

**Mock 的時機**：在單元測試中，用來取代**外部、慢、不穩定或有副作用**的依賴，例如資料庫、第三方 API、寄信、目前時間。

注意不要過度 Mock：如果 Mock 掉太多，測試只是在驗證 Mock 本身。資料存取邏輯更適合用整合測試（例如 Testcontainers 啟動真實資料庫）。

### Q5. 你們團隊的分支策略是什麼？為什麼？

這題沒有標準答案，重點是**說出選擇的理由**。回答範例：

「我們用 GitHub Flow：main 永遠可部署，每個功能開短期分支，透過 PR 做 Code Review 與 CI 測試後合併，合併後自動部署到測試環境。選它是因為我們每週部署多次，Git Flow 的 develop 與 release 分支對我們來說太繁重。未完成的功能會用 Feature Flag 關閉，避免長期分支造成合併衝突。」

若團隊有固定發版週期（如韌體或套裝軟體），說明採用 Git Flow 的理由也可以。

## 過時技術（知道就好）

- **SVN、TFS（TFVC）**：集中式版控，已被 Git 取代。
- **瀑布式開發**：仍見於法規嚴格產業（醫療、車用韌體），但多數團隊轉為敏捷。

## 本章回顧

- Git 分支策略取決於部署頻率
- 原則的核心都是「降低修改成本」
- 測試多寫單元測試，少量 E2E
