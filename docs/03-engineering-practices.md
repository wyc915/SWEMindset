# 03. 軟體工程實務

> **一句話**：會寫程式不等於會做軟體。版本控制、程式碼品質、測試，決定你的程式能不能被團隊長期維護。

---

## 1. Git 與分支策略 🟢

**必懂概念**：commit（存檔點）、branch（平行開發線）、merge（合併）、rebase（把提交接到最新基底上，歷史較乾淨）、PR / MR（請求審查後合併）。

| 策略 | 做法 | 適合 |
|---|---|---|
| **GitHub Flow** | main + 短期功能分支 + PR | 多數 Web 團隊，持續部署 |
| **Trunk-Based** | 極短分支、每天合併到 main，未完成功能用 Feature Flag 關閉 | 高頻部署團隊（業界主流方向） |
| **Git Flow** | main / develop / feature / release / hotfix | 有固定發版週期（如韌體、套裝軟體） |

**實用規範**：
- Commit 訊息：`feat:` 新功能、`fix:` 修 bug、`docs:` 文件（Conventional Commits）
- 版本號 **SemVer**：`主版號.次版號.修訂號`，破壞相容才升主版號

## 2. 程式碼品質原則 🟢

| 原則 | 白話解釋 |
|---|---|
| **單一職責** | 一個類別只做一件事，改動理由只有一個 |
| **開放封閉** | 加新功能時新增程式碼，而不是改舊程式碼 |
| **依賴反轉 / 依賴注入（DI）** | 依賴「介面」而不是具體實作，方便替換與測試（ASP.NET Core 內建 DI） |
| **DRY** | 同一個業務規則只寫在一個地方 |
| **KISS / YAGNI** | 保持簡單；現在不需要的功能不要做 |
| **高內聚、低耦合** | 相關的放一起，模組之間少牽扯 |
| **組合優於繼承** | 繼承太深會僵化，改用組合 |

> SOLID 的五個字母面試常考：單一職責、開放封閉、里氏替換、介面隔離、依賴反轉。

## 3. 設計模式：知道「解決什麼問題」即可 🟡

| 模式 | 解決的問題 | 生活例子 |
|---|---|---|
| **Factory** | 建立物件的邏輯集中管理 | 依參數產生不同付款方式物件 |
| **Singleton** | 全域只需一個實例 | 設定管理器（現多改用 DI 容器管理生命週期） |
| **Strategy** | 演算法可抽換 | 不同運費計算規則 |
| **Observer** | 狀態改變時通知訂閱者 | 事件、前端響應式資料 |
| **Adapter** | 讓不相容的介面能接起來 | 包裝第三方 API |
| **Decorator** | 不改原類別就加功能 | 加上日誌、快取 |
| **Repository** | 隔離資料存取邏輯 | 業務程式不直接寫 SQL |

## 4. 測試 🟢→🟡

**測試金字塔**：

```
      /  E2E  \        少量：模擬使用者操作，慢、易壞
     / 整合測試 \       適量：測模組與資料庫、API 的串接
    /  單元測試  \      大量：測單一函式邏輯，快、穩
```

- **Mock / Stub**：用假物件取代外部依賴（資料庫、第三方 API），讓單元測試只測自己。
- **TDD**：先寫測試再寫程式，逼你先想清楚需求。
- **覆蓋率不是目標**：重點是核心邏輯與邊界條件（空值、極大值、錯誤輸入）。
- 主流工具：xUnit（.NET）、Jest / Vitest（JS）、pytest、Playwright（E2E）。

## 5. 團隊協作 🟢

- **Code Review**：看正確性、可讀性、安全性；格式交給 Linter / Formatter 自動處理。
- **敏捷 / Scrum**：以 1～2 週為一個 Sprint，持續交付、定期回顧改進。
- **文件**：README（怎麼跑起來）、API 文件（OpenAPI）、ADR（為什麼這樣決定）。

## 過時技術（知道就好）

- **SVN、TFS（TFVC）**：集中式版控，已被 Git 取代。
- **瀑布式開發**：仍見於法規嚴格產業（醫療、車用韌體），但多數團隊轉為敏捷。

## 本章回顧

- Git 分支策略取決於部署頻率
- 原則的核心都是「降低修改成本」
- 測試多寫單元測試，少量 E2E
